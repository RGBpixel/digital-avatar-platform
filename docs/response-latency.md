# 对话回复延迟修复
2026-10-13：用户明确慢在文字出现之前。实测原企业前台豆包Seed2.0Pro完整回答9.930秒。

已实现：POST /api/chat-stream同源文字流；前端收到文字即显示，完整一句进入声音队列，声音与后续模型生成并行。使用同一取消控制，中途停止、换场所或换客人取消未完成文字和声音；不把思维链展示为回答。保留原chat与规则建档接口。
豆包Seed2支持回复方式fast/deep，默认快速接待，thinking.type=disabled，深度模式enabled。其他提供商不发送这项豆包专用参数。保持模型名称、密钥、云端许可与真人档案使用权限。

54项测试通过，包括SSE回答与思维链分离、快速与深度参数、文字断流检查及首句拆分。
真实同问题请求“你好，请问你们老板在吗？”：首批文字1.758秒，首句完整2.184秒，首句音频2.600秒，完整文字2.633秒；TTS首块0.416秒，reasoningChars=0。详见data/response-latency-verification.json。
独立既有合成音频的本机转写1.422秒，HTTP1.481秒；此音频与聊天问题不是同一条，不应把它们相加冒充真人端到端实测。以上模型时间从发送问题计，不含录音停顿、ASR和浏览器播放延迟。结果为单次、网络和文字长度会变化，不承诺固定速度。

当前后台已重启并使用快速模式。浏览器控制连接超时，需用户刷新当前网页加载新脚本；实际音频播放与连续对话还需用户体验确认。

进一步缩短收音等待：默认停顿从1000ms改为600ms，可在展示页选择400/600/1000ms；回答后重新开麦从700ms改为250ms。实际检查间隔80ms，因此停顿值是门限，不是精确时间。更短停顿可能截断思考中的一句话，可切回1秒。本轮未改变识别模型或降低beam搜索准确率；实时真人体验待确认。跨端部署应让手机/边缘客户端负责收音与播放，推理通过现有可替换服务接口运行在服务器；现阶段未完成移动端部署与性能验证。

流式声音衔接：每句不再等待播放结束后才生成下一句，下一句合成与上一句播放并行，句间不清空PCM队列，整轮完成后统一等待音频播放结束。每句首个有效音块估算固定增益（0.7–1.5倍，峰值限制），后续音块沿用，静音不放大；不会逐块自动拉升音量。7项声音流/句队列测试通过。尚未验证真人浏览器听感；模型生成的韵律差异和网络供给不足导致的间隔仍可能存在。

2026-10-14持续对话后速度优化：现场首字2.31秒，但视频持续声可能把录音推到8秒上限。新增背景自适应断句开关（默认开，可关闭）：前景峰值超过基础阈值6倍后，以峰值30%作为结束检测参考并限幅0.03；不改变声纹0.65整句门槛。本人声音回落到较低背景声时按现有停顿提交；响度相近或多人重叠仍可能到8秒，不能保证区分所有背景。声音变轻时可能提前截断，可关闭开关。声纹/ASR响应新增计时，界面同时保留收音总长、末尾等待和模型首字耗时，收音总长包含讲话本身，不能当作模型计算时间。模拟RMS轨迹验证提前结束；真人延迟尚待验证。

现场回退：用户报告背景自适应断句使唤醒变慢并再现静默，撤销默认启用并暂停UI实验入口，旧浏览器保存的开启值强制迁移关闭，恢复固定停顿。实际页面一段整句0.4736被拒；之前成功一段声纹47ms、ASR141ms，不能据此声称计算造成主要变慢。声纹uncertain时最多15秒提示一次“这句我没听清，请再说一遍”，不放行原音频、不变更参考、不送云端；其他声纹明确拒绝仍保持安静。所有现场效果仍待用户验证，不再将合成音频通过等同可用。
